## 3. 사전 조사 결과. Penpot에서 확인한 설계

Penpot은 Clojure/ClojureScript(편집기·서버)와 Rust/WASM(새 렌더러)으로 작성됐다. TypeScript로 옮길 수 있는 것은 코드가 아니라 데이터 형태와 알고리즘이다.

### 3.1 기존 판단 정정

앞선 조사에서 "부모 기준 좌표로 바꿔야 Auto Layout이 된다"고 했다. Penpot 소스를 보면 틀린 판단이다. Penpot도 `x`, `y`, `selrect`를 **절대 좌표**로 저장한다. 대신 아래 세 가지를 갖고 있다.

1. 부모가 자식 순서를 직접 들고 있다. 프레임과 그룹의 `:shapes`가 자식 id의 순서 있는 벡터다. 레이어 순서와 z-order가 여기서 정해진다.
2. 모든 도형이 `:transform`, `:transform-inverse` 행렬과 `:points`를 가진다. 회전과 기울임이 좌표와 분리된다.
3. 레이아웃은 저장값이 아니라 계산 결과다. flex 계산(`calc-layout-data`)이 자식마다 modifier를 만들고, 이 modifier를 트리 아래로 전파한 뒤 절대 좌표에 반영한다.

따라서 Canvas Studio의 절대 좌표는 유지해도 된다. 바꿔야 하는 것은 자식 순서, 변형 행렬, modifier 전파 단계다.

### 3.3 라이선스 제약

Penpot은 MPL-2.0이다. MPL은 파일 단위 copyleft다. Penpot 파일을 TypeScript로 옮겨 적으면 그 파일은 MPL-2.0 파생물로 볼 여지가 있다. 이 계획은 다음 규칙을 따른다.

- 데이터 형태와 알고리즘은 읽고 이해한 뒤 직접 구현한다.
- 알고리즘을 줄 단위로 옮긴 파일이 생기면 해당 파일 상단에 MPL-2.0 고지와 원본 경로를 남기고 소스를 공개한다.
- 법률 판단이 아니라 보수적 운영 규칙이다. 외부 배포 전에는 별도로 확인한다.

## 4. 구현 방안 비교

| 방안 | 내용 | 도달 점수(추정) | 장점 | 단점 |
|---|---|---:|---|---|
| A. Canvas Studio 재설계 | Penpot 설계를 참조해 9단계로 직접 구현 | 약 78 | 코드와 모델을 완전히 소유한다. `.fig`와 React 출력에 맞춘 모델을 설계할 수 있다. | 범위가 Penpot 전체에 가깝다. 협업에는 서버가 필요하다. |

| C. 범위 재정의 | "`.fig` 프레임 가져오기, 편집, React 출력" 흐름 전용 척도로 90점을 노린다 | 해당 척도 90 | 이 저장소의 차별점에 집중한다. 가장 짧다. | Figma 대체 편집기가 되지 않는다. |

**추천은 C를 목표로 두고 A의 1~5단계를 실행하는 것이다.** 1~5단계는 C의 흐름에 그대로 필요하고, 6단계 이후(벡터, 프로토타입, 협업, 렌더러)는 C에 필요하지 않다. 사용자가 Figma 대체 편집기 자체를 원한다면 B가 더 빠르다. 이 선택은 제품 방향 결정이라 사용자가 정한다.

## 6. 단계별 계획 (방안 A)

각 단계는 하나의 브랜치와 PR로 끝나고, 앞 단계의 테스트가 모두 통과한 상태에서 시작한다. 점수는 단계 완료 시점의 누적 추정치다. 크기는 S(며칠), M(1~2주), L(수주), XL(수개월)의 상대 규모이며 추정이다.

- 크기 입력값이 0 이하가 되지 않게 막는다. 근거 `app/src/App.tsx:302`.
- 열기와 가져오기 전에 현재 문서를 history에 남긴다. 근거 `app/src/App.tsx:221`, `:235`.
- 자동 저장을 드래그 종료 시점으로 미루고, TSX 생성은 코드 창이 열렸을 때만 한다. 근거 `app/src/App.tsx:107`, `:162`.
- Ctrl+휠 확대를 non-passive 리스너로 옮긴다. 근거 `app/src/App.tsx:201`.
- 완료 기준. 너비를 비운 뒤 새로고침해도 문서가 남는다. 227노드 문서를 드래그하는 동안 localStorage 쓰기가 0회다.

### 1단계. 문서 모델 v2와 변경 기반 히스토리 (→ 12점, M)

참조 `types/shape.cljc`, `shape_tree.cljc`, `files/changes.cljc`, `changes_builder.cljc`.

- 문서를 `pages[]`와 페이지별 `objects: Record<id, Shape>`로 바꾼다. 루트 프레임 id를 둔다.
- 컨테이너(frame, group)는 순서 있는 `children: id[]`를 갖는다. 레이어 목록과 z-order는 이 배열에서 나온다.
- `transform`(2×3 행렬)과 `rotation`을 추가한다. 좌표는 지금처럼 절대값으로 둔다.
- 모든 편집을 `Change` 목록(`addObj`, `modObj{ops}`, `delObj`, `movObjects`)으로 표현한다. 변경을 만들 때 되돌리는 변경도 함께 만든다. undo는 문서 사본 대신 되돌리는 변경을 적용한다.
- 입력 중 연속 수정은 한 묶음(transaction)으로 합쳐 undo 한 번에 되돌린다.
- v1 JSON을 v2로 바꾸는 마이그레이션을 만들고 테스트한다.
- 완료 기준. 기존 테스트와 v1 샘플 문서가 v2에서 같은 화면을 낸다. 글자 10개를 입력해도 undo 한 번에 되돌아간다.

### 4단계. Flex·Grid 레이아웃과 제약 (→ 44점, L)

참조 `types/shape/layout.cljc`, `geom/shapes/flex_layout/*`, `geom/shapes/grid_layout/*`, `geom/shapes/constraints.cljc`.

- 레이아웃 속성은 Penpot 스키마를 그대로 따른다. 방향, wrap, gap(row/column), padding p1~p4, justify/align, 자식의 fill/fix/auto 크기, min/max, absolute 자식.
- 레이아웃 계산을 순수 함수로 만들고 결과를 modifier로 반환한다. 편집할 때마다 바뀐 컨테이너부터 위쪽으로 다시 계산해 절대 좌표에 반영한다.
- 레이아웃이 없는 프레임의 자식에는 constraints(left/right/center/scale)를 적용한다.
- Figma `stackMode`, `stackSpacing`, padding, 크기 모드를 가져온다.
- React 출력에서 레이아웃 컨테이너를 CSS flex/grid로, 고정 좌표는 absolute 자식에만 쓴다.
- 완료 기준. `Contents`의 세로 Auto Layout(패딩 50/120, 간격 80)이 캔버스와 생성 CSS에서 같은 좌표를 낸다(SPEC M1 3번). 생성 TSX가 별도 Vite 프로젝트에서 빌드된다.

### 5단계. 컴포넌트, variant, 토큰 (→ 58점, L)

참조 `types/component.cljc`, `logic/libraries.cljc`, `types/variant.cljc`, `logic/variants.cljc`, `types/tokens_lib.cljc`.

- 메인 컴포넌트와 인스턴스를 `componentId`, `mainInstance`, `shapeRef`로 연결한다.
- 속성을 동기화 그룹으로 나누고, 인스턴스에서 바꾼 그룹을 `touched`로 기록한다. 메인을 고치면 touched가 아닌 그룹만 인스턴스에 전파한다.

- 완료 기준. `docs/implementation-plan.md`의 첫 검증 시나리오(버튼 컴포넌트, 인스턴스 변경, `label`·`variant`·`disabled` props)를 통과한다.

여기까지가 방안 C에 필요한 범위다. C 척도에서는 이 시점을 90점 목표 지점으로 본다.

### 6단계. 벡터·펜·불리언 (→ 61점, M)

참조 `frontend/src/app/main/data/workspace/{path,bool}.cljs`. 패스 편집, 펜 도구, 합치기·빼기·교차.

### 7단계. 프로토타입과 보기 모드 (→ 67점, M)

참조 `types/shape/interactions.cljc`. 클릭·호버 트리거, 화면 이동, 오버레이, 스크롤 고정, 발표 모드.

### 8단계. 협업 서버와 코멘트 (→ 73점, XL)

참조 `backend/`(구조만). 1단계 변경 모델을 WebSocket으로 주고받고, 서버가 순서를 정해 적용한다. 계정, 파일 목록, 코멘트, 버전 기록. 서버 운영과 인증이 생기므로 보안 규칙(CLAUDE.md)의 대상이 크게 늘어난다.

### 9단계. 성능과 확장 (→ 약 78점, XL)

참조 `render-wasm/src`. 대용량 문서에서 DOM 렌더 한계를 측정하고 Canvas/WebGL 타일 렌더러로 교체한다. 플러그인 API를 공개한다.

## 7. 90점에 닿지 않는 이유

| 남는 점수 | 이유 |
|---|---|
| 성능 3점 | Figma 수준의 수만 노드 실시간 편집은 전용 렌더러와 장기 최적화가 필요하다. Penpot도 2026년 기준 WebGL 렌더러가 베타다. |
| 생태계 4점 | 플러그인 수와 AI 기능은 사용자 기반이 만드는 점수다. 코드로 채울 수 없다. |
| 협업 2점, 프로토타입 3점 | 대규모 동시 편집 품질과 고급 인터랙션(변수, 조건, 스마트 애니메이트)은 8·7단계 범위를 넘는다. |

## 8. 제약사항과 극복 방안

| 제약 | 극복 |
|---|---|
| Penpot은 Clojure라 코드 재사용 불가 | 스키마와 알고리즘만 참조하고 TS로 직접 작성한다. 단계마다 참조 파일을 고정 커밋으로 기록한다. |
| MPL-2.0 | 3.3절 규칙을 따른다. |
| Figma 편집 동작 비교용 파일이 보기 권한 | 2단계 전에 편집 가능한 테스트 파일이 필요하다(기존 SPEC M2와 같음). |
| 50MB `.fig`의 브라우저 처리 | 0단계 뒤 Web Worker로 옮기고 파싱 시간을 측정한다. |
| 단일 `App.tsx` | 1단계의 모델·변경 경계가 생긴 뒤 2단계에서 canvas, panels, editor 모듈로 나눈다. 그 전에 나누지 않는다. |
| Windows 11 환경 | Node 24, PowerShell 명령으로 검증한다. 8단계 서버도 Windows에서 로컬 실행 가능해야 한다. |
